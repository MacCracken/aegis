# aegis P(-1) Hardening Audit — 2026-08-24

> **Cycle**: 1.1.6, paired with the 1.1.x minor per the CLAUDE.md P(-1) cadence.
> **Inputs**: full source review of all 3064 lines of `src/` (`lib.cyr` 2117,
> `pam.cyr` 747, `firewall.cyr` 172, `main.cyr` 28) across five dimensions —
> PAM security, memory safety, untrusted-input handling, functional correctness,
> and efficiency — each finding then re-derived from source by an independent
> adversarial pass before being accepted. Every accepted finding was
> additionally reproduced by the maintainer against the actual source or a
> compiled probe.
> **Output**: 18 findings (F-10..F-27), **all fixed in 1.1.6**. One candidate
> finding was refuted during verification and is recorded below rather than
> silently dropped.

**Why this pass found so much**: `src/pam.cyr` was folded in from agnosys at
1.1.0 and had never been audited — the 2026-05-10 pass predates it. It also had
**zero test assertions** and none of its symbols were in the API snapshot, so
three of the four gates that protect the rest of the library did not cover it.
That gap is closed here: pam.cyr is now in the test TU, carries 7 dedicated test
groups, and its 63 public symbols are in the regenerated snapshot.

## Severity legend

- **CRITICAL** — remote / privilege escalation; fix in this cycle, no excuses.
- **HIGH** — moderate effort to exploit, real-world consequences.
- **MEDIUM** — specific conditions required, or DoS-class.
- **LOW** — defense-in-depth.
- **INFO** — design observation, no exploitable hit.

## F-10 — `iso8601_parse` fed a `Str*` where a cstr is required

**Severity**: HIGH | **Status**: Fixed in 1.1.6.

**Root cause**: `iso8601_parse(s)` (lib/chrono.cyr:289) takes an *untyped*
parameter and immediately does `strlen(s)` and `load8(s + n)` — i.e. it requires
a **cstr**. Four sites in `src/lib.cyr` handed it a **`Str*` fat pointer**
instead: three wrapped an already-unwrapped cstr back up with `str_from(ts_cstr)`
(lines 1671, 1903, 1989) and one passed `json_v_str(arv)` directly (line 1933),
which also returns a `Str*`. `strlen` then walked the 16-byte Str header, which
contains a pointer and therefore NUL bytes, so the length always came out
`< 19` and the function returned its `-1` error sentinel.

This is precisely the boundary [ADR 0002](../adr/0002-cstr-api-boundary.md)
exists to prevent, and the untyped parameter meant the compiler could not catch it.

**Exposure**: Direct hit on the wire format daimon and argonaut consume. **Every
timestamp crossing the JSON boundary was `-1`** — `SecurityEvent.timestamp`,
`QuarantineEntry.auto_release_at`, `SecurityScanResult.scanned_at`. For
`auto_release_at` the damage compounds: `-1` *is* `AEGIS_AUTO_RELEASE_NONE`, so a
deserialized quarantine entry silently became one that never auto-releases.

**Reproduced**: compiled probe against the real library —
`iso8601_parse("2026-05-10T12:34:56Z")` → `1778416496`;
`iso8601_parse(str_from("2026-05-10T12:34:56Z"))` → `-1`.

**Fix**: pass the cstr at all four sites (`iso8601_parse(ts_cstr)`, and
`iso8601_parse(str_data(json_v_str(arv)))`).

**Test**: `p16_timestamp_roundtrip` — asserts a fresh event's timestamp is not
`-1`, and that it survives a `to_json` → `from_json` round-trip unchanged; same
for `SecurityScanResult.scanned_at`. **No test asserted any timestamp round-trip
before this cut**, which is why the bug shipped.

**CVE family**: CWE-843 Access of Resource Using Incompatible Type.

## F-11 — PAM rule denylist omits the render delimiters → auth-bypass write primitive

**Severity**: HIGH | **Status**: Fixed in 1.1.6.

**Root cause**: `pam_validate_rule` was the file's only sanitizer and it was a
**denylist** of exactly ten shell metacharacters (`| ; & $ ` > < ! { }`), applied
to the module path and to each argument. Bytes 9 (TAB), 10 (LF) and 13 (CR) were
not in the list — and the rendering context is delimited by exactly those bytes:
`pam_render_rule` joins fields with TAB and `pam_render_config` joins lines with
LF. Every other validator in aegis is an **allowlist** (`_aegis_valid_agent_id`,
`_aegis_valid_agent_addr`) precisely because F-2 established that denylists lose;
pam.cyr never got that treatment.

**Exposure**: A consumer that builds a rule from an attacker-influenced policy
field and renders it into `/etc/pam.d/<service>` gets arbitrary PAM stack
entries. `pam_rule_new(PAM_TYPE_AUTH, PAM_CTL_REQUIRED,
str_from("pam_unix.so\nauth\tsufficient\tpam_permit.so"), ...)` validated clean
and rendered as two lines; the injected one is `auth sufficient pam_permit.so`,
which returns `PAM_SUCCESS` unconditionally and short-circuits the stack —
**every password authenticates for that service**. Same class as F-2 (nftables
comment injection); worse consequence.

Reachability is consumer-mediated: the *parse* path cannot produce an embedded LF
(lines are split on LF first, then on whitespace), so this is an API-contract
defect on the construct-then-render path — which is exactly the path
`pam_rule_new` + `pam_validate_rule` exist to serve.

**Fix**: replaced both denylist loops with allowlists over printable ASCII plus an
explicit punctuation set (`_pam_valid_module`, `_pam_valid_arg`, built on
`_pam_str_allowed`), which rejects TAB/LF/CR/NUL and every high byte in one
clause. The `..` traversal check is kept. Additionally, **rendering now fails
closed**: `pam_render_rule` returns `0` for a rule that would not validate, and
`pam_render_config` refuses the whole document rather than silently dropping a
rule — dropping a `required` line weakens the stack just as surely as injecting
one.

**Contract change**: `pam_render_rule` / `pam_render_config` previously always
returned a Str. They now return `0` on invalid input, matching the F-2/F-3
precedent where the firewall builders return `0` rather than emitting a
dangerous ruleset.

**Test**: `p16_pam_validate_rule_rejects_delimiters`,
`p16_pam_render_fails_closed`.

**CVE family**: CWE-93 Improper Neutralization of CRLF Sequences; CWE-184
Incomplete List of Disallowed Input.

## F-12 — Unvalidated service name concatenated into a path; blocking open

**Severity**: HIGH | **Status**: Fixed in 1.1.6.

**Root cause**: `pam_read_service_config` concatenated the caller's
`service_name` straight onto `"/etc/pam.d/"` with no validation, then opened the
result with a bare `sys_open(path, O_RDONLY, 0)` — no `O_NOFOLLOW`, no
`O_CLOEXEC`. The correct pattern already existed in this repo from F-6
(`_aegis_stat_modesize`: open-no-follow + fstat + close). The asymmetry *inside
pam.cyr* is the tell that this was an oversight rather than a decision:
`pam_get_user_info` validates its username before touching the filesystem;
`pam_read_service_config` validated nothing.

**Exposure**: two hits against a root-privileged daemon.

1. **Permanent DoS.** An unprivileged local user creates a FIFO. A consumer calls
   `pam_read_service_config("../../tmp/hang")`; the path resolves out of
   `/etc/pam.d`, and a bare `O_RDONLY` open on a FIFO with no writer blocks in
   the kernel indefinitely — there is no `O_NONBLOCK`. The daemon thread never
   returns.
2. **Traversal.** `"../shadow"` opens `/etc/shadow` as root. `pam_parse_config`
   then errors on the content, so this is an existence/permission oracle rather
   than a direct dump — but it is an unvalidated root-privileged open of an
   arbitrary path, and any file whose lines happen to parse as PAM rules is
   returned to the caller verbatim.

**Fix**: `_pam_valid_service_name` — allowlist `[A-Za-z0-9._-]`, length 1..64,
leading `.` rejected (which kills `.`, `..` and dotfiles), `/` excluded by
construction. Rejected before any filesystem call. All three opens in the file
(`/etc/pam.d/<svc>` and the two `/etc/passwd` reads) now use
`O_RDONLY | O_CLOEXEC | _PAM_O_NOFOLLOW`.

**Test**: `p16_pam_service_name_rejects_traversal`.

**CVE family**: CWE-22 Path Traversal; CWE-410 Insufficient Resource Pool
(blocking open).

## F-13 — Absent JSON boolean defaulted to `0`, disabling auto-quarantine

**Severity**: HIGH | **Status**: Fixed in 1.1.6.

**Root cause**: `aegis_config_from_json_v` built its record from a bare
`alloc(AEGIS_CONFIG_SIZE)` and filled every field from
`_aegis_jv_get_bool(v, key)`, which returns `0` for an **absent** key — the same
value it returns for an explicit `false`. A document that simply omitted
`quarantine_on_critical` therefore deserialized to a config with auto-quarantine
**off**, silently, on the daemon's primary enforcement switch. Fail-open.

**Exposure**: any peer that emits a partial config document. A full
`to_json` → `from_json` round-trip is unaffected because the writer always emits
every key, which is why no existing test caught it.

**Fix**: start from `aegis_config_default()` and overwrite a field only when the
key is actually present (`_aegis_jv_set_bool_into`, and a presence check on the
two clamped integers). Absent → safe default; explicit `false` → still honoured.

**Test**: `p16_config_partial_json_fails_closed` — asserts a partial document
keeps the defaults *and* that an explicit `false` still wins.

**CVE family**: CWE-1188 Insecure Default Initialization of Resource.

## F-14 — F-7's agent_id whitelist not enforced at the deserialization seam

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: F-7 (0.9.4) hardened `security_event_new` and the three
quarantine entry points with the `_aegis_valid_agent_id` whitelist, but
`security_event_from_json_v` builds its record by direct `store64` and never ran
it. The serde door was left open on a fix that closed the constructor door.

**Exposure**: a wire event can carry an `agent_id` outside the whitelist. Feed
that event to `aegis_report_event` and the auto-quarantine path creates an entry
keyed by an id that `aegis_release_agent` and `aegis_get_quarantine` will then
refuse to act on — an entry nothing can clear.

**Fix**: run `_aegis_valid_agent_id_or_empty` on the deserialized value; a
non-conforming id is stripped to `None`, matching what `security_event_new`
already does.

**Test**: `p16_serde_rejects_bad_agent_id`.

**CVE family**: CWE-20 Improper Input Validation. Recorded as **F-7 reopening at
a seam the original fix did not cover**, not as an independent finding.

## F-15 — Unvalidated ThreatLevel indexes a 5-slot inline array

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: `threat_counts` is an inline `i64[5]` inside the daemon record at
offset 32, immediately after `scan_history` at offset 24 (ADR 0003).
`aegis_threat_count(d, level)` and `_aegis_inc_threat_count(d, level)` computed
`d + 32 + level * 8` with no bounds check, so an out-of-range level is a direct
OOB index: `-1` lands on `scan_history` and corrupts a live vec pointer; `>= 5`
walks off the end of the record.

**Exposure**: not reachable from wire input — `threat_level_from_serde` returns
`-1` and every in-tree caller gates on `parsed >= 0`. But both functions are
public entry points and the level is supplied by the consumer, so the contract
is what is at stake.

**Fix**: `_aegis_threat_level_ok` gate on both. Out-of-range reads return `0`;
out-of-range increments are a no-op.

**Test**: `p16_threat_count_bounds` — asserts the OOB increment leaves the
adjacent `scan_history` pointer intact.

**CVE family**: CWE-129 Improper Validation of Array Index.

## F-16 — Non-numeric UID in a passwd line parses as `0` (root)

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: `pam_parse_passwd_line` checked only that the UID and GID fields
were non-empty, then called `str_to_int` on them. `str_to_int` (lib/str.cyr:280)
**skips non-digit bytes silently** and returns `0` for a wholly non-numeric
field. So `alice:x:root:root:...` parsed to `uid 0, gid 0`, and the
`uid < 1000` heuristic then marked it `is_system = 1`. The code's own comment
claimed this was checked ("check that string actually looks numeric"); it was not.

**Exposure**: a security daemon reporting user identity that maps a malformed
entry onto root. Poisoning `/etc/passwd` needs root, so the practical exposure is
misreporting on a corrupt or hand-edited file rather than a privilege boundary —
but "unparseable means root" is the wrong failure direction for this component.

**Fix**: `_pam_all_digits` on both fields; a non-numeric field is an `Err`.

**Test**: `p16_pam_passwd_rejects_non_numeric_uid` — including that a genuine
`root:x:0:0` line still parses and is still flagged as a system user.

**CVE family**: CWE-704 Incorrect Type Conversion.

## F-17 — One-byte heap write past the end of the `who` capture buffer

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: `pam_list_sessions` allocated exactly 16384 bytes, passed 16384
as `run_capture`'s cap, and then wrote a NUL at `buf + nbytes`. `run_capture`
(lib/process.cyr:99-108) exits its read loop on `total >= buflen` and returns
`Ok(total)` — so `total` can be exactly `16384`, and the terminator lands one
byte past the allocation. `pam_read_fd_to_str` in the same file gets this right
(`alloc(cap + 1)`); this site did not.

**Exposure**: needs `who` to emit ≥16 KB, which a busy multi-user host reaches.
The written value is `0` and the immediately-adjacent object today is
`run_capture`'s own `Ok` result tag, so the concrete effect is currently nil —
but it is a genuine out-of-bounds write and one allocation-order change makes it
live.

**Fix**: `alloc(_PAM_WHO_CAP + 1)` with `_PAM_WHO_CAP` passed as the cap, matching
`pam_read_fd_to_str`.

**CVE family**: CWE-193 Off-by-one Error; CWE-787 Out-of-bounds Write.

## F-18 — Parsed PAM/passwd fields were not NUL-terminated

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: `str_new` and `str_sub` (lib/str.cyr:51, 201) build a Str header
that **shares the parent's buffer and does not NUL-terminate** — only
`str_clone` allocates `len + 1` and terminates. `pam_split_whitespace`,
`pam_parse_passwd_line` and `pam_parse_who_output` stored such borrowed Strs
directly into `pam_rule`, `pam_user` and `pam_session` records, all of which
expose them through public getters. [ADR 0002](../adr/0002-cstr-api-boundary.md)
makes `str_data(s)` the documented way for a consumer to unwrap one.

**Exposure**: `str_data(pam_user_username(u))` returned a pointer into the middle
of the source line, so reading it as a cstr yielded
`"alice:x:1000:1000::/home/alice:/bin/sh"` instead of `"alice"` — the rest of the
passwd entry, including the shell and home path, disclosed through a field that
claims to be just the username. Same for `pam_session_user`,
`pam_session_remote_host`, `pam_rule_module` and every rule argument.

**Discovered by**: the new PAM test group, on its first run. Not surfaced by the
source review — a concrete assertion found what reading did not.

**Fix**: `str_clone` every parsed value that reaches a record field.

**CVE family**: CWE-125 Out-of-bounds Read.

## F-19 — `pam_parse_config` rejected the grammar it exists to audit

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: the parser accepted only `type control module [args...]` with
`type` in `{auth, account, session, password}` and `control` one of five bare
keywords. Real Linux-PAM grammar has two more forms it rejected outright, and a
rejection fails the **whole file**:

- a leading `-` on the type (`-auth`, `-session`) meaning "skip silently if the
  module is absent";
- the bracketed `value=action` control form, e.g. `[success=1 default=bad]`,
  which additionally contains spaces and so had already been torn into several
  tokens by `pam_split_whitespace`.

**Exposure**: measured against this host's own `/etc/pam.d`: **14 lines use the
`-` prefix** and the central `system-auth` file — which most other services
`include` — uses bracket syntax. aegis could not read the PAM stack it exists to
audit. A security daemon that reports "cannot parse" for the real configuration
provides no coverage at all.

**Fix**: `pam_rule` grows from 4 fields to 6 — `optional` (the `-` prefix) and
`control_text` (the raw bracket expression). `PAM_CTL_BRACKET` is added to
`PamControlId`. The parser strips and records the `-`, rejoins bracket tokens
from `[` to the token ending in `]` (rejecting an unterminated expression), and
the renderer reproduces both verbatim so a parsed config round-trips
byte-for-byte instead of being flattened into a different policy. The bracket
text is validated as an injection sink like any other rendered field.

**Test**: `p16_pam_parse_real_world_grammar` — parses a config using both forms,
checks the captured fields, and asserts the render reproduces the `-` prefix and
the bracket expression.

## F-20 — `scan_result_from_json_v` trusted the wire `clean` flag

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: the deserializer read `clean` straight from the document instead
of deriving it from the findings it had just deserialized. `_scan_result_seal`
exists for exactly this and was not called.

**Exposure**: a peer sending a findings array alongside `"clean": true` has its
failing scan read as passing.

**Fix**: call `_scan_result_seal(r)` after populating the findings vec.

**Test**: `p16_scan_clean_resealed_from_findings`.

**CVE family**: CWE-349 Acceptance of Extraneous Untrusted Data With Trusted Data.

## F-21 — Read errors indistinguishable from end-of-file

**Severity**: MEDIUM | **Status**: Fixed in 1.1.6.

**Root cause**: `pam_read_fd_to_str`'s loop treated any `n <= 0` from `sys_read`
as EOF, including `-EINTR`.

**Exposure**: a signal arriving mid-read silently truncates the security config
being parsed. Truncating a PAM stack after a `sufficient` line but before the
`required` line that follows it means aegis reports a weaker policy than the one
on disk.

**Fix**: retry on `-EINTR` rather than treating it as EOF.

## F-22 — `max_connections_per_agent` was the one unclamped wire integer

**Severity**: LOW | **Status**: Fixed in 1.1.6.

F-1/F-4/F-5 clamped `max_events`, `auto_release_timeout_secs` and
`periodic_scan_interval_secs`. `DatabaseSecurityPolicy.max_connections_per_agent`
rides the same wire and reaches consumer scheduling logic unbounded, including
negative. Fixed with `_aegis_clamp_max_conns` (`AEGIS_MAX_CONNS_HARD_CAP` =
65535; negative → 0). Test: `p16_max_conns_clamped`.

**CVE family**: CWE-770 Allocation of Resources Without Limits.

## F-23 — Log messages built before the level filter ran

**Severity**: LOW (efficiency) | **Status**: Fixed in 1.1.6.

sakshi's level filter runs *inside* `sakshi_debug`/`info`/`warn` — by then the
caller has already allocated a `str_builder`, appended every key/value pair, and
built the final Str. At the default `SK_INFO` level all eight debug lines in
`src/lib.cyr` were constructed and thrown away on every call. `_aegis_span_enter`
already guarded spans this way; the message blocks did not.

Fixed with `_aegis_log_want_debug()` guards around the eight debug construction
blocks, mirroring the existing span guard.

## F-24 — Redundant hash+probe on every map point lookup

**Severity**: LOW (efficiency) | **Status**: Fixed in 1.1.6.

Four sites did `map_has(m, k)` immediately followed by `map_get(m, k)` — two full
hash-and-probe passes for one piece of information. Values in these maps are
pointers and are never `0`, so a non-zero `map_get` *is* the "present" answer.
Two of the four are on `aegis_report_event`'s path, which runs for every
CRITICAL/HIGH event. `aegis_get_quarantine` additionally re-read
`aegis_quarantine(d)` three times where one local would do.

## F-25 — O(n) count of an O(1) quantity; avoidable strlen on the hot path

**Severity**: LOW (efficiency) | **Status**: Fixed in 1.1.6.

- `aegis_stats` computed the quarantine count as
  `vec_len(aegis_quarantined_agents(d))` — `map_keys` plus one `map_get` per key,
  building a whole vec to discard everything but its length. `map_size` is O(1)
  and provably equal (the hashmap maintains the count on insert and delete).
- `_aegis_uuid_to_string` ended with `return str_from(hex)`, running a 36-byte
  `strlen` over a buffer whose exact length it had just computed in `pos`.
  `str_new(hex, pos)` is the same result without the scan. This runs once per
  `security_event_new` via `aegis_next_id` — the hottest path in the library.

Benchmark effect: `aegis_next_id` 837 ns → 804 ns.

## F-26 — `pam_validate_rule` duplicated a 75-line denylist verbatim

**Severity**: INFO (duplication) | **Status**: Fixed in 1.1.6.

The module check and the argument check were the same ten byte values in the same

## F-27 — pam.cyr sat outside three of four quality gates

**Severity**: INFO | **Status**: Fixed in 1.1.6.

`tests/aegis.tcyr` included `src/lib.cyr` and `src/firewall.cyr` but not
`src/pam.cyr`; `grep -c pam_ tests/aegis.tcyr` returned **0**. None of its
symbols appeared in the API snapshot. This is the direct reason F-11, F-12, F-16,
F-17, F-18 and F-19 survived a release cut.

Two related gate defects found in the same pass and fixed here:

- **The F-8 regression test was inert.** It passed `str_data(huge)` — a cstr — to
  parsers that take a `Str`, so `_aegis_json_size_ok`'s `str_len` read character
  bytes as a length field. The test passed for the wrong reason and never
  exercised the length cap. It now passes the `Str`, asserts the input really is
  oversize, and adds an under-cap acceptance case.
- **The three test harnesses called `syscall(60, ...)`** — the Linux exit number
  literal. Per the genesis CLAUDE.md rule this is a no-op on agnos, where `exit`
  is syscall 0; `SYS_EXIT` resolves correctly on both. Now `SYS_EXIT`.

`src/pam.cyr` is now in the test TU with 7 dedicated groups, and its 63 public
symbols are in the regenerated snapshot.

## Refuted during verification

One candidate finding did not survive the adversarial pass and is recorded here
rather than dropped, so a future audit does not re-derive it:

- **"37 `stik_err_*` call sites in pam.cyr pass a bare cstr where a `Str` is
  required."** Refuted. The error constructors accept the cstr form at these call
  sites; the claimed type mismatch does not exist. No change made.

A second proposal — recycling per-call heap in pam.cyr's entry points — was
verified as describing a real property of the bump allocator but with a fix that
was **wrong as written**, and was not applied. The underlying observation (aegis
never frees; steady-state memory tracks total events reported, not ring capacity)
is a real characteristic of the allocator rather than a defect in aegis, and is
recorded in [`state.md`](../development/state.md) rather than as a finding.

## Method note

Findings were produced by five independent source reviews, one per dimension,
each followed by a separate adversarial pass whose explicit instruction was to
**refute** rather than confirm — defaulting to rejection whenever the defect could
not be independently re-derived from source. Severities in the table above are
post-verification: eight were revised down and one claim was refuted outright.
Every accepted finding was then reproduced by the maintainer directly, and F-10
was confirmed by compiling a probe against the real library rather than by
reading.

The pattern worth carrying forward: **the test suite found F-18 on its first
run**, after three separate review passes over the same function had missed it.
Concrete assertions catch what reading does not.
