# aegis P(-1) Hardening Audit — 2026-11-04

> **Cycle**: 1.2.2, paired with the 1.2.x minor per the CLAUDE.md P(-1) cadence.
> **Inputs**: all 3,420 lines of `src/` at 1.2.1 (`lib.cyr` 2,296, `pam.cyr` 906,
> `firewall.cyr` 172, `main.cyr` 46). Two independent source reviews ran, one
> over `lib.cyr` + `main.cyr` and one over `pam.cyr` + `firewall.cyr`, alongside
> the maintainer's own pass. Code added since the last audit, and never
> reviewed, was the NDJSON event sink (1.1.7). Every accepted finding was
> re-derived from source by the maintainer, and its regression test was run
> against the 1.2.1 sources to confirm it fails there. "Confirmed" lines below
> also include the reviewers' probes. Behavioural claims were run against real
> systems: the installed `nft` 1.1.7, `qemu-aarch64`, and two network namespaces
> joined by a veth pair.
> **Output**: 21 findings (F-28..F-48). **20 are fixed in 1.2.2.** F-47 is
> deferred to 1.3.x; it fails closed today.

**Why this pass found so much.** Three causes account for most of it:

- **aarch64 was built but never run.** CI cross-compiled aarch64 and shipped the
  binary in releases, but never ran the suite there. The existing suite catches
  F-28 under qemu on its first run.
- **The firewall builders were tested for "non-null", not for "validates".**
  An IPv6 isolate has never produced a ruleset nft accepts (F-38). The 1.0
  good-input test passed it anyway.
- **The PAM parser was written against its own idea of the grammar.**
  `libpam_internal/pam_line.c` defines what Linux-PAM actually reads, and the two
  disagree in ways an attacker can use (F-44).

## Severity legend

- **CRITICAL** — remote / privilege escalation; fix in this cycle, no excuses.
- **HIGH** — moderate effort to exploit, real-world consequences.
- **MEDIUM** — specific conditions required, or DoS-class.
- **LOW** — defense-in-depth.
- **INFO** — design observation, no exploitable hit.

## F-28 — The x86_64 value of `O_NOFOLLOW` on aarch64

**Severity**: HIGH | **Status**: Fixed in 1.2.2.

`src/lib.cyr` and `src/pam.cyr` each defined `O_NOFOLLOW` locally as `131072`. A
comment said it was verified against `asm-generic/fcntl.h` "on every Linux arch aegis
targets", but arm64 overrides that header. There `0x20000` is `O_LARGEFILE` and
`O_NOFOLLOW` is `0x8000`.

**Effect on the aarch64 build** (shipped by `release.yml`): every "no-follow" open
followed symlinks. That voided two earlier HIGH fixes on that build:

- the scanner's F-6 (open-no-follow + fstat);
- the PAM reads' F-12 (`/etc/pam.d/<service>`, `/etc/passwd`).

**Confirmed** under `qemu-aarch64`. A probe's no-follow stat of a symlink returned 1
(followed), against 0 on x86_64. The unmodified 1.2.1 test suite fails 2 of its 428
assertions on aarch64, both in `p1_scan_refuses_to_follow_symlink`.

**Fix**: both local constants are gone. The open sites use the stdlib's `O_NOFOLLOW`,
which is defined per arch since cyrius 6.6.4 (and in `lib/io.cyr` for agnos). The
stdlib comment records the same failure in patra. See F-48 for the gate.

## F-38 — An agent with an IPv6 address can never be isolated or rate-limited

**Severity**: HIGH | **Status**: Fixed in 1.2.2.

`aegis_isolate_agent` / `aegis_rate_limit_agent` accept IPv6 addresses, but always used
`match_dest_addr` / `match_source_addr`, which nein renders as `ip daddr` /
`ip saddr`. nft refuses an IPv6 address there.

**Effect**: `aegis_firewall_validate` returned 1 for every IPv6 agent, so `QA_ISOLATE`
and `QA_RATELIMIT` were never enforced for them. Loaded in one `nft -f` batch with other
tables, the ruleset fails the whole batch. The 1.0 test `p1_firewall_accepts_good_input`
asserted only a non-null pointer.

**Fix**: an address with ':' uses `match_dest_addr6` / `match_source_addr6`. The new
test asserts `validate == 0`, and checks that `ip6 daddr` / `ip6 saddr` appear in the
rendered ruleset. Both IPv6 rulesets pass the installed `nft -c`.

## F-29 — The event sink follows a planted symlink and trusts a pre-existing file

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

`aegis_set_event_sink` (1.1.7) opened `O_WRONLY|O_CREAT|O_APPEND`. The daemon that calls
it runs privileged. Three problems:

- **A symlink at the path is followed.** If `AEGIS_EVENT_LOG` names a path in a
  directory another user can write, they can aim the appends at any file. A
  description such as `"x /tmp/evil.so"` appended to `/etc/ld.so.preload` is root
  code execution.
- **A file someone else created first stays theirs.** Mode 0600 applies only at
  creation, so its owner can read the stream and append forged records that a
  consumer (chakshu) reads as aegis events.
- **A FIFO at the path hangs daemon startup.**

**Confirmed**: the open followed a symlink to a 0644 file and appended to it, and the
mode stayed 0644.

**Fix**: the open adds `O_NOFOLLOW|O_NONBLOCK` (a FIFO with no reader fails with ENXIO).
It then fstats the file and requires a regular file, owned by the effective uid, with
one link. It returns `-EINVAL` / `-EPERM` otherwise. A symlink, a FIFO and a hard link
are each tested.

## F-30 — A FIFO at a scan path hangs the daemon; a directory scans clean

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

The scanners called the stdlib's `file_exists`, a bare `O_RDONLY` open that follows
symlinks, before `_aegis_stat_modesize`, which had no `O_NONBLOCK`. Two effects:

- **A FIFO with no writer blocks either open forever.** Confirmed: on 1.2.1,
  `aegis_scan_agent` on a FIFO is killed by `timeout`.
- **No file-type check.** A directory, socket or device that opens is judged by size and
  mode alone, so a directory passed as a clean agent binary.

The same `file_exists` sat in front of the data-directory check.

**Fix**:

- `_aegis_path_present` lstats the path instead of opening it.
- `_aegis_stat_modesize` adds `O_NONBLOCK`.
- Both scanners report a new `not_regular_file` finding (THREAT_HIGH) for anything that
  is not a regular file.

A dangling symlink now reports `unreadable_metadata` rather than `missing_binary`.

## F-31 — A failed or short sink write glues two records together

**Severity**: LOW | **Status**: Fixed in 1.2.2.

`_aegis_event_sink_write` returned the `sys_write` result, and its only caller ignored
it. A short write (disk full, `RLIMIT_FSIZE`) left a fragment with no newline, and the
next record was appended to it. A reader then lost both records.

**Confirmed**: under `RLIMIT_FSIZE=700`, a Python reader rejected the glued 699-byte
line. The comment's claim that a reader stopping at the last newline "can never observe
a torn record" did not hold after a failure.

**Fix**: the sink tracks a torn tail. It is set by a short write, or found at open, when
the file's last byte is not `\n`. The next record then starts with a newline, which ends
the fragment as its own line, so one record is lost, not two. A failed write is logged
at warn with its rc.

## F-32 — The PostgreSQL socket-permission check could never fire

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

`_aegis_check_pg_socket` used `file_exists` and `_aegis_stat_modesize`, and both
`open()` the path. `open(2)` on a UNIX socket fails with ENXIO, so the function returned
before checking anything, and `check_socket_permissions = 1` did nothing.

**Fix**: lstat the path and judge only an `S_IFSOCK`. The check moved into
`_aegis_check_socket_at(findings, path)` so the test can bind a real socket and flip its
mode.

## F-33 — A present key of the wrong type turns enforcement off

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2. Reopens F-13.

F-13 made absent keys keep their defaults. A present key of the wrong type did not:
`_aegis_jv_set_bool_into` stored `json_v_bool(v)`, and bayan answers 0 for anything
that is not a bool.

**Confirmed**: `{"quarantine_on_critical":1,"quarantine_on_high":"true","scan_on_execute":null}`
disabled all three switches, and a CRITICAL event then returned `QA_NONE`.
`periodic_scan_interval_secs` sent as a string came out as 0.

`dbpolicy_from_json_v` still started from a zeroed record, which is the exact F-13
pattern. `{"kernel_tuning":[]}` produced a policy with:

- `audit_ddl` and `check_socket_permissions` off;
- empty data-directory paths (an empty path is skipped silently);
- a connection ceiling of 0, which disables it.

**Fix**:

- Bools are stored only when the value is a JSON bool.
- The clamped numeric fields are stored only when the value is a number.
- The DB policy reader starts from `database_security_policy_default()`.
- An explicit `false`, and an explicit empty `kernel_tuning`, are still honoured.

## F-34 — An empty agent_id makes a quarantine entry nothing can clear

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

`security_event_new` used `_aegis_valid_agent_id_or_empty`, so `""` was stored as an
empty `Str`. `security_event_from_json_v` did the same. `_aegis_report_event_inner`
tests only for a null pointer, so it auto-quarantined the key `""` and returned
`QA_TERMINATE`. `aegis_is_quarantined("")` and `aegis_release_agent("")` use the strict
whitelist and refuse `""`, so the entry stayed in the map and the stats for good.

**Fix**: `""` is None (an anonymous event) in both constructors. The "or empty"
variant is removed.

## F-35 — An embedded NUL passes the agent_id whitelist at the serde seam

**Severity**: LOW | **Status**: Fixed in 1.2.2.

`security_event_from_json_v` validated `str_data(json_v_str(v))`, a C string that ends
at the first NUL, and then stored the whole `Str`.

**Confirmed** with `"good\u0000; flush ruleset"`, a `Str` of length 20:

- the daemon quarantined `good`;
- `aegis_events_for_agent("good")` found no events;
- re-serialising the event published the full string downstream.

**Fix**: the whitelist must pass, and `strlen` must equal `str_len`.

## F-36 — `stats_threat_count` had no bounds check

**Severity**: LOW | **Status**: Fixed in 1.2.2. Sibling of F-15.

F-15 bounded `aegis_threat_count`, but its `AegisStats` twin `stats_threat_count` read
`s + 32 + level*8` unchecked. Level -1 returned `scans_completed`, and level 5 or above
read past the 72-byte record. It now uses `_aegis_threat_level_ok`.

## F-37 — Hot-path log lines built below their level

**Severity**: LOW | **Status**: Fixed in 1.2.2. Completes F-23.

F-23 guarded the debug lines. `_aegis_report_event_inner` still built its info line and
both warn lines with a `str_builder` before sakshi's level filter dropped them. They are
now guarded by `_aegis_log_want_info` / `_aegis_log_want_warn`. The bench runs at
`SK_ERROR`: `aegis_report_event` 3.381 µs → 2.499 µs (−26%).

## F-39 — An agent_id with '.' builds a firewall that never validates

**Severity**: LOW | **Status**: Fixed in 1.2.2.

aegis's id whitelist allows '.', and nein's nft-name check does not. So
`aegis_isolate_agent("a.b", …)` returned a firewall that fails validation, while
`aegis_quarantine_agent("a.b")` succeeded. The agent was recorded as isolated, with no
ruleset a validating consumer could apply.

**Fix**: the builders run nein's `validate_nft_name` on the composed table name and
return 0. The id whitelist itself is unchanged, because the quarantine path still
accepts '.'.

## F-40 — The hardened-host baseline cuts off all IPv6, SSH included

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

With input policy drop and only IPv4 echo allowed, ICMPv6 neighbour discovery is
dropped. Conntrack does not track ND, so the established/related rule never matches it.

**Confirmed** with two namespaces on a veth pair: TCP/22 over IPv6 failed under the
1.2.1 ruleset (the peer's neighbour entry went FAILED) and connected under 1.2.2's.
IPv4 was unaffected both times.

**Fix**: three accept rules, for `nd-neighbor-solicit`, `nd-neighbor-advert` and
`nd-router-advert`. They are new rules with new comments, and no existing rule changed.

## F-41 — The firewall address was checked by character set only

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

`_aegis_valid_agent_addr` allows `[0-9a-fA-F:./]`, length 1–43, and nothing more. The
builders used it alone, and `aegis_firewall_render` rendered whatever it was handed.
That is ADR 0006's own failure mode. Accepted inputs included:

- **Hex-only host names** (`dead.beef`, `c0ffee.cafe`, `fade.de`). nft resolves them
  through DNS at apply time. Confirmed with a hosts entry: the applied rule became
  `ip daddr 10.9.8.7 drop`, so whoever controls the name chooses which address is
  blocked.
- **Out-of-range and malformed addresses**: `999.1.1.1`, `10.0.0.1/33`, `::::`.
- **Any prefix, including `/0`.** That validates, and drops all IPv4 traffic both ways
  at priority -1, SSH included.

Two smaller gaps sat in the same seam:

- **No upper bound on `pps`.** At 2³¹ or above, the burst exceeds nft's u32 and
  validation fails. Above 2⁶² the burst goes negative.
- **No null check.** `aegis_firewall_validate(0)` and `aegis_firewall_render(0)`
  segfaulted, though 0 is the builders' documented failure value.

**Fix**:

- **Address:** the builders require the whitelist, then nein's `validate_addr` (a
  literal address, never a name), then a single host: no prefix, `/32` or `/128`.
- **`pps`:** capped at 2³¹−1.
- **Null:** `validate(0)` returns 1 and `render(0)` returns 0.
- **Render:** `aegis_firewall_render` goes through `firewall_render_checked` and returns
  0 for a firewall that does not validate. That brings it in line with ADR 0006
  ("every aegis function that emits security-relevant text refuses rather than emits").

## F-42 — Security files over the read cap were silently truncated

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2. Reopens F-21.

`pam_read_fd_to_str(fd, cap)` stopped at `cap` (8 KB for `/etc/pam.d/<service>`, 64 KB
for `/etc/passwd`) and at the first read error, and returned what it had. F-21 fixed
only EINTR.

**Confirmed**: an 8,163-byte comment, then `auth sufficient pam_unix.so`, then
`auth required pam_deny.so`, parsed as Ok with one rule. The `required` line was gone.
A larger `/etc/passwd` returned a partial user list.

**Fix**: the three security reads use `_pam_read_whole`. It sizes its buffer from fstat
and refuses a file over the cap, one that grows past its fstat size while being read,
and any read error. The caps are now 256 KB for service files and 16 MB for passwd, so
real hosts don't start failing where they used to be truncated. Small files cost what
they cost before. `pam_read_fd_to_str` keeps its documented behaviour for other
callers.

## F-43 — An overflowing uid parsed as root

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2. Reopens F-16.

F-16 required the uid and gid fields to be all digits, but `str_to_int` wraps.

**Confirmed**:

- `18446744073709551616` parsed as uid 0, `is_system = 1`.
- `9223372036854775808` parsed as INT64_MIN, `is_system = 1`.

**Fix**: `_pam_id_ok` allows 1–10 digits and a value of at most 4294967294.
`(uid_t)-1` is the "no change" sentinel, so it is refused too.

## F-44 — PAM line assembly differed from Linux-PAM

**Severity**: MEDIUM | **Status**: Fixed in 1.2.2.

`pam_parse_config` split on `\n` and skipped only lines that start with `#`. Linux-PAM
(`libpam_internal/pam_line.c`, `_pam_line_assemble`) differs in two ways:

- a line whose last non-blank byte is `\` continues onto the next line;
- `#` anywhere starts a comment.

**The evasion**: `auth optional pam_permit.so \` followed by `auth required pam_unix.so`.

- **Linux-PAM** reads one rule, optional pam_permit. As the only module in the stack,
  its success passes, so no password is needed.
- **aegis** audited two rules, one of them `required pam_unix.so`.

A trailing `# comment` also became three bogus arguments.

**Fix**: `_pam_assemble_lines` follows `pam_line.c`:

- `#` ends the line, and a line holding one never continues;
- a backslash after trailing spaces and tabs joins the next line. A CR is not blank,
  as in Linux-PAM;
- blank lines and comment-only lines are skipped;
- a file that ends inside a continuation is an error.

The renderer's allowlist already keeps `#` and `\` out of rendered rules, so the
output side needed no change.

## F-45 — Rule type, control and optional were not range-checked

**Severity**: LOW | **Status**: Fixed in 1.2.2.

`pam_validate_rule` checked the module and arguments, but not the enum fields. A rule
built with type 99 rendered as `unknown\tunknown\tpam_unix.so`, and Linux-PAM marks an
illegal-type line as must-fail, so every login for that service fails. Type, control
and optional are now range-checked.

## F-46 — The bracket control's shape was not checked

**Severity**: LOW | **Status**: Fixed in 1.2.2.

A control text of `[success=ok] x` validated and rendered verbatim. Linux-PAM ends the
control at the first `]`, so it loads module `x`, and the module aegis validated
(`pam_unix.so`) becomes an argument.

**Fix**: the control must be a single `[...]` group with no bracket inside. This is
enforced both when validating and when parsing.

## F-47 — The parser rejects grammar that real systems use

**Severity**: MEDIUM | **Status**: Deferred to 1.3.x (roadmap). Fails closed today.

Each of these makes `pam_parse_config` return Err for the whole file:

- upper-case keywords (`AUTH Required`), which Linux-PAM accepts;
- the `substack` control, used by Fedora/RHEL's sshd and login stacks;
- `@include`, used on Debian.

On RHEL, authselect makes `system-auth` a symlink, which the no-follow open refuses.

None of these is an evasion: aegis refuses to audit the file rather than misreading it.
But it cannot audit those hosts at all. Supporting them adds grammar: a
`PAM_CTL_SUBSTACK` constant and an include directive. That is public surface, so it
belongs in the next minor, not a patch.

## F-48 — Gate coverage

**Severity**: INFO | **Status**: Fixed in 1.2.2.

- **aarch64 was cross-built but never run**, which is why F-28 shipped. CI and
  `scripts/audit.sh` now run the test suite under `qemu-aarch64`, with the same
  `cycc_aarch64` skip rule. `release.yml` calls `ci.yml`, so releases are gated too.
- **The version gate matched any substring.** `grep -q "$VERSION" CHANGELOG.md` passed
  1.2.1 before its entry existed, because `1.2.1` already appeared as a dependency
  version. CI and `audit.sh` now require a `## [X.Y.Z]` heading.
- **CI's lint step** assigned `out=$(cyrius lint …)` without the `|| true` that
  `audit.sh` has. Under the runner's `bash -e`, a non-zero lint exit ended the step
  before printing its output.
- **CLAUDE.md said function-scope `var buf[N]` is static data.** Since cyrius 6.3.15
  it is per-call stack storage up to the per-fn frame budget (~120 KB), and static only
  above that, with a compiler warning. Confirmed with a recursion probe. CLAUDE.md and
  the CI comment are corrected.

## Noted, not changed

- **`run_capture` returns Ok when `/usr/bin/who` is missing**, so `pam_list_sessions`
  answers Ok with no sessions, which looks the same as nobody logged in. Recorded for
  the F-47 work.
- **The event sink opens without `O_NOCTTY`.** The fstat check refuses a tty, but only
  after the open. The stdlib defines no `O_NOCTTY`, and pointing `AEGIS_EVENT_LOG` at a
  tty is an operator's own choice.
- **The sink check depends on fstat, which agnos lacks**, so the sink refuses to open
  on `--agnos` builds. Its open ABI is already wrong there; see roadmap 1.4.x.

## Rejected during verification

- **Quarantine-map keys borrow the caller's buffer.** ADR 0002 makes the caller
  responsible for keeping it alive.
- **Unbounded `q_events` / `scan_history` growth.** This is the never-free bump
  allocator, already recorded in `state.md`.
- **The sink can emit a raw newline.** It cannot: bayan escapes `\n`, `\r` and every
  byte below 0x20, metadata keys included. High bytes pass through raw (INFO).
- **The `stik_err_*` cstr arguments.** The 2026-08-24 refutation holds.
- **Result handling at the destructured sites** (`pam.cyr` list_users, list_sessions,
  get_user_info) is correct.

## Method note

Two reviewers each took half of `src/` with no knowledge of the other's findings or the
maintainer's. The firewall reviewer and the maintainer both found F-39; nothing else
overlapped. The maintainer found F-28 while checking the roadmap's stale `O_NOFOLLOW`
item.

The pattern worth carrying forward is **run the claim against the real thing**:

- F-28 needed aarch64 itself;
- F-38 and F-41 needed nft;
- F-40 needed two hosts on a link;
- F-44 needed Linux-PAM's own source.

Reading aegis alone would have found none of them. And as in 2026-08-24, the suite
caught a regression as soon as it ran somewhere new: the two assertions that catch F-28
have existed since 0.9.5, and were never run on the architecture they protect.
